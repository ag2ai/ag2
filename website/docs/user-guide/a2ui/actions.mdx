A2UI **actions** are the clickable parts of a UI — buttons that, when pressed, drive what happens next. A clickable button is a function you decorate with `#!python @a2ui_action` and **declare on the transport** via `#!python actions=[...]` — the agent stays a plain `#!python Agent`. The transport advertises the button to the LLM so it can render it; a click runs your function **on the server**, the agent is not invoked.

## Server-Side Buttons (`@a2ui_action`)

Decorate a function with `#!python @a2ui_action`, then declare it on the server with `#!python actions=`. The button is declared to the LLM so it can render it, but a **click runs the function on the server** with the click's `#!python event.context` as keyword arguments — the agent is **not** invoked. Inside the handler you can do anything: hit a backend, call a tool, update a surface.

```python linenums="1" hl_lines="6-11 15"
from ag2 import Agent
from ag2.a2ui import A2UIServer, a2ui_action
from ag2.a2ui.transports import RestTransport
from ag2.config import AnthropicConfig

@a2ui_action(description="Schedule all posts for the given time")
def schedule_posts(time: str) -> dict:
    # ... do the work on the server ...
    return {"updateComponents": {"surfaceId": "s1", "components": [
        {"id": "root", "component": "Text", "text": f"Scheduled for {time}"},
    ]}}

agent = Agent(name="ui_agent", config=AnthropicConfig(model="claude-sonnet-5"))

app = A2UIServer(agent, transport=RestTransport(encoding="jsonl"), actions=[schedule_posts])
```

When the LLM renders a button whose `#!python action.event.name` is `#!python "schedule_posts"`, a click sends the button's `#!python event.context` back as the handler's keyword arguments and runs it on the server. The decorator derives an example context from the function's parameter schema (here `#!python {"time": "<string>"}`) and injects it into the system prompt so the LLM emits the right keys; pass `#!python example_context=` to override it.

What the handler returns is mapped to the client per the A2UI spec:

- one A2UI server→client message — or a list of them (e.g. `#!python updateComponents` / `#!python updateDataModel`) — is sent to the renderer as a **surface update** (works on every protocol version);
- any other JSON value is dropped: a click is fire-and-forget. To get a value back, the renderer [calls the action as a function](#calling-an-action-as-a-function-v10) instead.

With `#!python validate_responses=True` (the default), the returned messages are [validated](#what-validation-checks) like the model's. Invalid messages are not sent; a warning naming the handler and the errors is logged. Validation knows only the catalogs configured on the server (see [custom catalogs](/docs/user-guide/a2ui/capabilities)), so a handler's `#!python callRendererFunction` must name a function declared there, with `#!python allowedCallers` admitting the agent. A result that only partly looks like messages (several message keys in one object, or a list mixing messages with other values) is treated as a plain value, also with a warning.

A turn whose only input is registered server-action interactions **skips the agent entirely** — the handlers' messages are the whole response.

Declaring the button on the transport — not on the agent — keeps the `#!python Agent` plain and reusable across deployments. The same `#!python actions=[...]` is accepted by `#!python A2UIAgentExecutor` for the [A2A transport](/docs/user-guide/a2ui/a2a), so a button is declared the same way wherever the agent is served.

## Other Kinds of Buttons

A2UI components support two button shapes the spec distinguishes by what the click does:

- **Server `#!python event`** — sends a client→server message; the server handles it. This is what `#!python @a2ui_action` produces.
- **Client `#!python functionCall`** — runs a function **on the renderer with no network round-trip** (e.g. `#!python openUrl`, copy-to-clipboard).

Client `#!python functionCall` buttons execute entirely in the client, so they are **not registered on the server**. The LLM learns which client functions it may target from the active **catalog** and from the client's advertised [capabilities](/docs/user-guide/a2ui/capabilities) — not from server-side code. You can also render a button whose `#!python event.name` isn't backed by a registered action: a click on it is rewritten generically into the next prompt so the LLM simply continues the conversation.

In v1.0, a component's explicit `#!python @catalogId` or a function call's explicit `#!python catalogId` selects its definition. Otherwise, validation inherits the surface catalog from a `#!python createSurface` in the same response. For updates to a surface created in an earlier response, the server does not retain its catalog binding: implicit components and function calls are accepted if a configured catalog supports them. Use explicit `#!python @catalogId` / `#!python catalogId` values when validation must select particular definitions across responses. The renderer still resolves implicit references against its surface's catalog.

## The Click Round-Trip

The server is stateless, so a click is just another request. The client posts the conversation plus an `#!python a2ui` envelope describing what was pressed; the server runs the matching handler — or, for an unregistered button, rewrites the click into the current turn:

```python linenums="1" hl_lines="4-15"
import httpx

body = {
    "messages": [],  # plus any prior conversation
    "a2ui": [
        {
            "version": "v0.9",
            "action": {
                "name": "schedule_posts",
                "surfaceId": "s1",
                "sourceComponentId": "schedule_btn",
                "timestamp": "2026-06-17T12:00:00Z",
                "context": {"time": "2:00 PM"},
            },
        }
    ],
}

async with httpx.AsyncClient(base_url="http://127.0.0.1:8000") as client:
    resp = await client.post("/a2ui", json=body)
```

When the action name matches a registered `#!python @a2ui_action`, the click runs that handler on the server (the agent is not invoked); otherwise the click is rewritten into a plain instruction so the LLM continues the conversation.

!!! note "v1.0 round-trip"
    With `#!python protocol_version="v1.0"`, a renderer's reply to a `#!python callRendererFunction` the LLM emitted arrives as a `#!python rendererFunctionResponse` envelope in the next request and is rewritten to a continuation prompt. On the stateless REST transport, the prompt carries the call ID and its value or error; include conversation history when the model also needs the originating call's context. A2A keeps the task in `#!python input-required` until the renderer responds.

## Calling an Action as a Function (v1.0)

A v1.0 renderer that needs a *value* back — verifying an id, a typeahead, an inventory check — sends a `#!python callAgentFunction` envelope instead of a click. The function name (`#!python callFunction["@call"]`) selects a registered `#!python @a2ui_action`, and `#!python args` become its keyword arguments. The server answers with an `#!python agentFunctionResponse` that echoes the call's `#!python functionCallId`; the agent is not invoked:

```json
{
  "a2uiRendererCapabilities": {
    "1.0": {"supportedCatalogIds": ["https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json"]}
  },
  "a2ui": [
    {
      "version": "1.0",
      "callAgentFunction": {
        "surfaceId": "s1",
        "functionCallId": "verify-1",
        "callFunction": {"@call": "verify_provider", "args": {"provider_id": "PRV-102"}}
      }
    }
  ]
}
```

A v1.0 request carries the renderer's capabilities: one without them withdraws A2UI for its turn, so the call would get no answer (see [Capability negotiation](/docs/user-guide/a2ui/capabilities#client-capability-negotiation)).

```json
{"version": "1.0", "agentFunctionResponse": {"functionCallId": "verify-1", "value": {"valid": true}}}
```

`#!python verify_provider` does not have to be in the renderer's catalog: a renderer with no local implementation of a function routes the call to the agent. A renderer that rejects functions its catalogs don't name must declare the agent's functions, without implementing them.

Over [AG-UI](/docs/user-guide/a2ui/server#serving-over-ag-ui-copilotkit) the same envelope rides `#!python forwardedProps.a2uiAction` (or in a list under `#!python forwardedProps.a2ui`), and the `#!python agentFunctionResponse` comes back in the run's `#!python ACTIVITY_SNAPSHOT`.

The reply is always exactly one of `#!python value` or `#!python error`. Any messages the handler returns (an `#!python updateDataModel`, say) are sent first, and then the response carries `#!python null`. A failure is reported rather than raised:

| `#!python error.code` | When |
|---|---|
| `#!python UNKNOWN_FUNCTION` | No action is registered under that name, or an explicit `#!python catalogId` names a catalog this turn does not offer (see [Capability negotiation](/docs/user-guide/a2ui/capabilities#client-capability-negotiation)). |
| `#!python INVALID_FUNCTION_CALL` | The envelope is malformed but carries a `#!python functionCallId` (a missing or empty `#!python surfaceId`, an empty `#!python @call`, as the official A2UI SDK also treats them; an unknown property, in the envelope or in `#!python callFunction`; a `#!python catalogId` that is not a string; `#!python args` that is not an object), or `#!python args` does not fit the handler's parameters, including unknown keyword names when the handler has no `#!python **kwargs`. An omitted `#!python args` uses the handler's defaults. |
| `#!python EXECUTION_ERROR` | The handler raised, returned messages that fail validation, or returned an `#!python agentFunctionResponse` of its own (the error text is logged, not sent to the renderer). |
| your own code | The handler raised `#!python A2UIFunctionError(code, message)`: the renderer gets that `#!python code` and `#!python message` as is, so keep the message fit for the user. |

```python
from ag2.a2ui import A2UIFunctionError, a2ui_action


KNOWN_PROVIDERS = {"PRV-102"}


@a2ui_action
async def verify_provider(provider_id: str) -> dict[str, bool]:
    if provider_id not in KNOWN_PROVIDERS:
        raise A2UIFunctionError("PROVIDER_NOT_FOUND", f"Unknown provider: {provider_id}.")
    return {"valid": True}
```

If `#!python callFunction` omits `#!python catalogId`, the call is still answered. The spec asks the renderer to send it, but the message schema does not require it, so the server does not reject a call without one.

Every envelope must conform to the served version's renderer→agent schema: exactly `#!python version` and one of `#!python action`, `#!python callAgentFunction`, `#!python rendererFunctionResponse` and `#!python error`; the version's own `#!python version` value; and each payload's required fields. An `#!python action` needs `#!python name`, `#!python surfaceId`, `#!python sourceComponentId`, a `#!python context` object and an RFC 3339 `#!python timestamp`. A malformed envelope is dropped with a warning: it reaches no handler, no prompt and no `#!python A2UIClientEvent`, and the turn is handed to the agent as usual. The one exception is a v1.0 `#!python callAgentFunction` that still carries a non-empty `#!python functionCallId`: the renderer is waiting on it, so the server answers `#!python INVALID_FUNCTION_CALL`. A call with an empty `#!python functionCallId` cannot be correlated, so it is dropped and its handler never runs.

`#!python callAgentFunction` and `#!python rendererFunctionResponse` do not exist before v1.0: on v0.9 and v0.9.1 they are dropped the same way.

## Observing Client Interactions

Each client→server interaction the server receives — a button `#!python action`, a v1.0 `#!python callAgentFunction` or `#!python rendererFunctionResponse`, or an `#!python error` — is surfaced on the turn's stream as an `#!python A2UIClientEvent`, the inbound mirror of `#!python A2UIMessageEvent`. Subscribe to react to or log client interactions (beyond what the LLM sees in its prompt):

```python linenums="1"
from ag2.a2ui import A2UIClientEvent

@stream.subscribe
async def on_client_event(event):
    if isinstance(event, A2UIClientEvent):
        log.info("client interaction: %r", event.interaction)
```

!!! note
    A purely client-side `#!python functionCall` button (e.g. `#!python openUrl`) runs on the renderer with no network round-trip per the A2UI spec, so it produces no envelope and therefore no `#!python A2UIClientEvent`.

## What Validation Checks

With `#!python validate_responses=True` (the default), every A2UI message the model emits, or a server-side handler returns, is checked before it reaches the client. All problems in a response are listed in one retry prompt.

- **Schema**: each message must match the protocol version's message schema and the catalog its surface or component names (the basic catalog, or the custom one; see [custom catalogs](/docs/user-guide/a2ui/capabilities)). A call to a function the catalog does not define reports `unknown function '<name>'`. A component naming an unregistered `#!python @catalogId` (v1.0), or a `#!python createSurface` whose `#!python catalogId` names a catalog the server does not have (any version), reports `unknown catalog '<id>'`; the components on such a surface are not checked further.
- **Catalog selection (v1.0)**: there is no default catalog. Each component and function call resolves against its own `#!python @catalogId` / `#!python catalogId`, or else the `#!python catalogId` of the `#!python createSurface` that created its surface in the same response. A component that has neither reports that it `names no '@catalogId' and the surface has no default 'catalogId'`. On a surface created in an earlier response, the server does not know the surface's catalog, so an implicit component or call is accepted if any configured catalog defines it; give it an explicit `#!python @catalogId` / `#!python catalogId` to select one.
- **Names (v1.0)**: component ids, and the ids that reference them, must be [UAX #31](https://www.unicode.org/reports/tr31/){.external-link target="_blank"} identifiers: a letter or `#!python _`, then letters, digits, combining marks or `#!python _`. A component of type `#!python Surface` is rejected: the name is reserved for the container `#!python createSurface` creates.
- **Surface lifecycle**: within one response, a surface may be created only once, may not be updated before the `#!python createSurface` that creates it, and may not be updated after a `#!python deleteSurface` removes it. Updates to a surface created in an earlier response are allowed.
- **Component tree**: component references are the properties whose schema refers to `#!python ComponentId`, `#!python Child` or `#!python ChildList` from `#!python common_types.json`. For a surface the response creates, every reference must resolve to a component on that surface, every component must be reachable from `#!python root`, there must be no reference cycles, and no id may appear twice in one message (a later message may update an earlier component by id). A surface created in an earlier response may be updated partially, so its references may point at earlier components; only duplicate ids and cycles among the response's own components are rejected there.
- **Data paths**: the `#!python path` of an `#!python updateDataModel` must be a [JSON Pointer](https://datatracker.ietf.org/doc/html/rfc6901){.external-link target="_blank"}, such as `#!python "/user/name"`.

With `#!python validate_responses=False`, nothing is rejected: the A2UI block is still split from the prose and sent as-is.

## Observing Validation Failures

A2UI has no server→client error message, so when the model can't produce schema-valid UI within `#!python validation_retries + 1` attempts, the agent **gracefully degrades** to prose and emits no `#!python A2UIMessageEvent`. To tell "couldn't build UI" apart from "intentionally answered with text", subscribe to `#!python A2UIValidationFailedEvent` on the stream:

```python linenums="1"
from ag2.a2ui import A2UIValidationFailedEvent

@stream.subscribe
async def on_validation_failed(event):
    if isinstance(event, A2UIValidationFailedEvent):
        log.warning("A2UI validation failed after %d attempts: %s", event.attempts, event.errors)
```
